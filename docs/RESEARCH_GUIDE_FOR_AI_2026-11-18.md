# SiliconLLM 研究完整说明与 AI 接续指南

更新日期：2026 年 11 月 18 日，Asia/Tokyo。

当前论文题目：**Performance Analysis and Adaptive Optimization of Local LLM Inference for Agentic Workloads**。

中文可理解为：面向 Agent 工作负载的本地大语言模型推理性能分析与自适应优化。

这是一项在 Apple Silicon 上进行的硕士研究。它从可修改的推理实现出发，逐步转向代码 Agent 场景中的历史草稿复用和动态解码控制。目标是减少实际推理时间，而不是训练一个新模型，也不是提高模型本身的代码能力。

本文件可以单独交给其他 AI 阅读。下文的项目路径用于定位证据和实现；接收 AI 若不能访问本机，需要另外取得对应文件，不能假装已经检查过它们。本文整理现有研究，不包含 11 月 18 日新跑的推理实验。

## 1. 先用几句话理解这项研究

代码 Agent 经常需要生成代码、运行测试、根据反馈修改代码。修改时，模型可能重新输出大量已经存在的内容。如果能从旧代码中找到便宜的候选 token，再让目标模型一次验证多个 token，就有机会减少逐 token 解码的开销。

但是，草稿不是越长越好。长草稿可能很早就被拒绝，验证和缓存处理也需要时间。因此，我们研究一个轻量控制器：**根据执行成本和近期匹配情况，决定这一步是否复用历史，以及最多复用多少 token。**

研究需要同时回答三个问题：

1. 历史草稿能否比普通解码更省时间？
2. 动态选择能否在相同历史来源、相同验证流程下，进一步优于固定长度草稿？
3. 收益能否保留到较完整的 mlx-lm 生成流程和真实 Agent 工作流，而不只存在于较慢的自定义循环？

截至当前，可以开始组织论文和汇报材料，但不能宣布所有实验已经结束。外部报告提供了动态控制的正向结果；本机另有小规模 API 接入结果。两者是不同的研究记录，不能互相替代。

## 3. 研究想解决什么问题

### 3.1 场景是本地代码 Agent

这里的 Agent 是一个小型代码修复工作流：

```text
任务和一个可见示例
    -> 模型生成完整 Python 代码
    -> 执行可见测试
    -> 失败时把错误反馈给模型
    -> 模型返回完整修改版代码
    -> 最多再修复两次
    -> 停止后执行最终评分测试
```

Agent 会多次调用同一个模型，并在后续调用中看到旧代码和反馈。这使历史内容成为一种自然的草稿来源。Agent 是推理优化的应用验证场景，不是新换的无关课题。

本研究不要求先选择一个商业 Agent 产品。项目已有自己的受限代码修复 harness，可以控制任务、测试、提示和修复次数。目前不是完整复现某个大型仓库 Agent，也不是多 Agent 调度研究。

### 3.2 为什么不直接用小模型生成草稿

常规投机解码可用较小模型生成候选，再交给目标模型批量验证。但在本项目早期的 0.5B 草稿、1.5B 目标组合中，小模型计算本身占用了较大时间，抵消了减少目标模型调用的收益。

这促使研究转向便宜的历史查找：如果旧代码已经存在，是否能直接从中复制候选，不再为每个草稿 token 跑一个小模型？这不是说小模型投机解码普遍无效，而是根据本地已测配置寻找更合适的方案。

### 3.3 最终目标和非目标

最终目标是在明确的本地工作负载上，测出比合适基线更低的延迟，并检查优化后是否保持该基线的完整贪心输出。

不以以下事情作为已实现目标：

- 训练新语言模型或修改目标模型权重。
- 让同一个模型解出更多代码题。
- 自动修复模型原本的逻辑错误。
- 击败所有推理引擎、所有投机方法或所有 Agent 系统。
- 用一次短样例测试证明所有输入都数值等价。

保存输出的优化也会保存错误答案。速度、输出一致性和任务成功率必须分开报告。

## 4. SiliconLLM 与各个 Stage 的关系

SiliconLLM 是基于 [skyzh/tiny-llm](https://github.com/skyzh/tiny-llm) 的个人研究 fork，提供可以修改、测试和计时的推理代码。内部包名仍为 `tiny_llm`，这不是另一个研究项目。

对外说明使用 Stage 1、Stage 2、Stage 3。部分课程目录、命令和代码文件仍叫 `week_1`、`qwen2_week2.py` 等；这是兼容既有教程和测试的名称，不代表报告应继续用 Week 命名。

| 阶段 | 主要工作 | 对当前研究的作用 |
| --- | --- | --- |
| Stage 1 | 模型前向、Attention、RoPE、GQA、归一化、MLP、采样与生成基线 | 建立可修改、可分析的实现基础 |
| Stage 2 | 持久 KV cache、正确性检查、性能归因和组件耗时分析 | 建立可靠的普通解码参考 |
| Stage 3 早期 | 小模型草稿的投机解码和成本拆分 | 发现减少目标前向不一定减少总耗时 |
| 当前延伸 | 历史草稿、成本控制、Agent 评估和 native/API 集成 | 形成需要实验支持的研究方法与应用验证 |

不能把课程 upstream 中列出的 Flash Attention、分页缓存、连续批处理、MoE、RAG 等能力全部当成本项目已经完成的研究成果。当前主线是解码、历史草稿和控制器，并非把所有 Stage 3 主题都做一遍。

### 4.1 早期 KV cache 结果应怎样理解

保存的 0.5B 三次重复归因实验中，Stage 2 full-context 控制为约 7.69 tok/s，Stage 2 持久 KV cache 为约 65.65 tok/s，decode 吞吐比约 **8.542x**。

这是同一实现框架下，有无持久解码缓存的比较，不是相对最佳 mlx-lm 的 8.5 倍提升。在该历史设置中，mlx-lm 仍约为 189.43 tok/s。KV cache 主要是工程基础和性能归因证据，不作为新的算法创新。

来源：`benches/stage2_attribution_benchmark_summary.csv`、`benches/stage2_attribution_benchmark_ratios.csv` 和 `docs/PHASE2_ATTRIBUTION_BENCHMARK_2026-05-30.md`。这些是保存的历史测量，不是 11 月 18 日新复测。

### 4.2 早期 profiler 得到了什么

Stage 1、Stage 2 都有组件分析记录。保存的 Stage 2、上下文长度 512 的单步 profile 中，Attention core 和 MLP 各约占 21%，QKV projection 约 14%，elementwise/norm 约 15%，KV 更新约 12%，Python loop/sampler 约 0.8%。

这说明在那个 profile 设置中，不能把剩余性能差距简单归因于 Python 循环。组件逐项同步计时还可能改变调度，因此不能把这些占比不加条件地套到完整 streaming API。

来源：`docs/PHASE2_STAGE2_DECODE_COMPONENT_PROFILE_2026-05-30.md` 和 `benches/stage2_decode_component_profile_summary.csv`。

### 4.3 小模型草稿的历史结果

早期 1.5B 目标、0.5B 草稿的三次重复记录中，k=2/4/8 的 decode 比约为 0.780x/0.710x/0.555x，均低于普通 KV-cache 基线。较长输出的后续扫描中，最佳配置也未超过 1.0x。

这些记录支持的结论是：**在已测原型中，小模型草稿成本过高，单纯减少目标调用不足以加速。** 它们不证明所有小模型方案都不值得做，也不证明历史草稿或动态控制没有意义。

来源：`benches/stage3_speculative_accounting_qwen2_1p5b_draft0p5b_summary.csv`、`docs/STAGE3_BREAK_EVEN_ANALYSIS_2026-10-15.md`。

## 5. 理解方法前需要的几个概念

### 5.1 Prefill 与 decode

Prefill 处理输入提示，建立其缓存。Decode 在已有上下文上逐个生成新 token。两部分的计算形状不同，优化其中一部分不一定等比例改善整个请求。

### 5.2 KV cache 不是历史草稿

KV cache 保存模型已经处理过的 token 对应的 Key 和 Value 张量，用于避免重复计算上下文。

历史草稿保存或检索的是旧文本的 token 序列，用于提出未来输出的候选。它不直接复用旧代码对应的 KV 张量，也不是把旧答案直接作为最终输出。

目前 Agent 的跨轮文本历史和单次调用中的 KV 状态是两件事。不要把“用前一次代码做草稿”写成“已经实现跨轮 KV cache 复用”。

### 5.3 固定历史草稿

先根据当前输出后缀检索旧 token 序列，取匹配位置后面的若干 token。固定策略使用最多 k 个候选；候选不足时可以更短，没有匹配时使用普通解码。k=16 不代表每一步强制提出 16 个 token。

### 5.4 投机验证

设最新已输出 token 为 x，它还没有作为输入写入当前缓存。历史给出草稿 A、B、C、D。

```text
目标模型输入：x A B C D
对应的后继预测：A B Z ? ?

草稿 A 与目标预测 A 一致：接受
草稿 B 与目标预测 B 一致：接受
草稿 C 与目标预测 Z 不一致：停止接受

本轮输出：A B Z
草稿剩余 C、D 不使用
```

所有符号都是示意 token，并不表示某个 Python 字符一定对应一个 token。批量验证能一次计算多个位置的预测，但有限精度下的批量前向与逐 token 前向仍可能存在数值差异，所以必须检查后续完整输出。

投机解码的一般背景可参考 [Fast Inference from Transformers via Speculative Decoding](https://arxiv.org/abs/2211.17192)。本项目当前研究的是贪心路径，不应把原论文更一般的采样分布保证直接当成我们有限精度实现已证明的性质。

### 5.5 两种 replay 不要混淆

| 术语 | 实际含义 |
| --- | --- |
| 固定输入 replay 评测 | 固定提示、已知历史和输出上限，把同一请求交给不同方法重新生成 |
| 恢复时的 replay | 在一次解码内部，恢复旧 KV 状态，再用普通前向重新处理保留前缀 |

前者是实验比较方式，后者是算法执行开销。文件名中有 replay，不能据此判断该方法一定做了缓存恢复重放。

## 6. 历史检索和动态控制具体怎样实现

### 6.1 历史检索

本地 `HistoryIndex` 是常规 n-gram 索引，默认 n=4：

1. 对每条可用 token 序列建立四 token 后缀到位置的索引。
2. 用当前已生成输出的最后四个 token 查找历史匹配。
3. 最多检查最近 32 个命中位置，取它们后面的候选续写。
4. 当前实现按候选出现次数、再按长度选择一个候选。
5. 已经生成的当前请求 token 也可加入索引；不同序列不会在索引中被直接拼成一条跨边界序列。

这不是新提出的检索算法。主比较中，固定策略和动态策略应使用同一历史来源，否则“更好的历史”与“更好的控制器”会混在一起。

允许使用的历史必须在决策时已知，例如同一任务之前的代码、明确提供的源文件、当前已经输出的 token。不能使用基线未来答案、隐藏测试反馈或尚未发生的修复轨迹。

### 6.2 本地现存控制器

`src/tiny_llm/adaptive_decode.py` 的 `CostPolicy` 提供一个可以核对的旧实现：

- 动作包括普通解码 k=0，以及可用的 k=2/4/8/16。
- 普通单步和不同验证长度的时间来自校准配置，评估时不根据最终结果重新选择它们。
- 接受率估计 p 和查找开销估计 L 在线更新。
- 比较每个候选动作的预计单位输出时间。
- 只有预计成本低于普通解码成本的 95%，才使用草稿，即保留约 5% 的预计收益余量。

本地类默认 p=0.8；研究 runner 可以从配置传入不同先验，不能把类默认值当作所有外部实验最终参数。当前更新规则为：

```text
p_new = 0.7 * p_old + 0.3 * (accepted / proposed)
L_new = 0.8 * L_old + 0.2 * observed_lookup_time
```

候选不足时，只比较能实际提出的长度。此实现不是一个已经学会识别代码语义或保证选择最优长度的模型。接受率也是简化的近期统计，不是完整条件概率模型。

### 6.3 一个高层伪代码

```text
对每个新的模型请求：
    建立该请求的 KV cache 和允许使用的历史索引
    重置本请求的控制器状态

每次解码：
    查询历史候选
    如果没有候选，走普通解码
    否则比较普通解码与可行草稿长度的预计成本
    若预计收益不足，走普通解码
    否则用目标模型批量验证所选草稿
    接受连续匹配前缀，取得目标 token
    按实际实现恢复或裁剪缓存
    更新当前输出、历史索引和统计量
    检查 EOS 和输出长度上限
```

这段伪代码描述方法结构，不代表新的 trim-only API 版本已经有动态控制器。当前 API pilot 只接入了固定草稿，见第 10 节。

### 6.4 接受率规则和反馈版不是同一方法

旧实现另有简单接受率规则：近期接受率达到阈值时使用最多 8 个草稿，否则不用。它用于判断成本模型是否比仅看接受率更有价值。

`warm_feedback` 则在控制器选择普通解码时，把该次普通 next-token 结果与第一个历史候选比较，用已有模型结果更新反馈，不为这个观察额外增加模型前向。

这个观察只涉及第一个候选 token。它不是多个候选连续接受率的无偏估计。反馈版也必须作为单独方法标识，不能把它的优势与原控制器的结果混成一个“最终版本”。

## 7. 成本公式与 replay、trim 的区别

### 7.1 基本选择分数

现有说明使用：

```text
C(k) = [V(k) + L + R(k)] / G(k)
```

| 符号 | 含义 |
| --- | --- |
| k | 提出的草稿 token 数量 |
| V(k) | 一轮目标验证的预计耗时，包含前向中的 KV cache 使用 |
| L | 历史检索的预计开销 |
| R(k) | 该实现额外缓存恢复处理的预计耗时 |
| G(k) | 本轮预计推进的输出 token 数 |
| T_step | 普通解码单步的校准耗时 |

分子、分母分别是“一轮大约花多少时间”和“一轮大约输出多少 token”。不能直接拿总耗时和单步耗时比较，而不考虑推进量。

当前分数不是已经验证准确的完整延迟预测器。索引维护、控制决策、同步等开销也要进入最终 wall time；其中哪些已被 V、L 或 R 包含，哪些还未显式建模，需要核对计时边界，避免漏算或重复计入。

### 7.2 预计输出推进量

在每个连续候选以相同概率 p 匹配的简化假设下：

```text
G(k) = 1 + p + p^2 + ... + p^k
```

这里的 1 表示目标模型给出的 correction 或 bonus token。这一近似忽略了接受概率随位置变化、相关性、EOS 和输出上限截断等因素，不能被描述为所有请求都成立的精确预测。

### 7.3 旧 snapshot、restore、replay 路径

本地旧 `decode()` 在投机验证前保存快照。如果发生拒绝，则恢复快照，用普通逐 token 前向重新处理保留前缀。模型重放过程中还会核对接受前缀，因此实际开销需要由运行记录确认。

假设拒绝前接受 j 个草稿，每次恢复确实需要 j+1 次普通前向，则旧近似为：

```text
R_replay(k)
    = T_step * sum((j + 1) * p^j * (1 - p), j = 0 ... k-1)
```

它估算的是“恢复时重新跑模型”的成本。代码中的全接受分支保留批量 cache，并非每次全接受都重放。若将来实现改变为全接受也重放，就必须加上对应项；不能沿用旧公式却说已经计入了所有恢复成本。

现有记录把采用 replay 的原因归于批量与单步执行可能产生的有限精度状态差异。具体 kernel 根因尚未隔离，不能把 replay 描述为 Apple Silicon、mlx-lm 或投机解码普遍必需的步骤。

### 7.4 Native mlx-lm trim 路径

对于这次使用的标准可裁剪 target KV cache，验证后的流程是：

```text
验证前 cache： earlier context
待处理输入：   x

验证输入：     x A B C D
临时 cache：   earlier context x A B C D

接受 A B，拒绝 C，目标给出 Z
裁剪后 cache： earlier context x A B
下一轮输入：   Z

下一次正常前向后：earlier context x A B Z
```

它保留已经接受的缓存条目，只裁掉被拒绝的后缀。Z 下一轮正常进入模型，不是重新跑 A、B 的恢复 replay。对应开销应按 cache trim 计，而不是乘以 j+1 次目标前向。

沿用上面的简化概率假设，可写为：

```text
R_trim(k)
    = sum(p^j * (1 - p) * T_trim(k - j), j = 0 ... k-1)
```

其中 T_trim(k-j) 是该分支裁掉剩余后缀的耗时。该表达式暂把全接受的额外恢复成本设为零；收尾裁剪或其他状态维护若有独立开销，应另行计入。不能未经测量就把整个 R(k) 直接写成零。

本机安装实现的技术依据是 `mlx_lm/generate.py` 和 `mlx_lm/models/cache.py`，版本 0.27.1。参考官方 [生成代码](https://github.com/ml-explore/mlx-lm/blob/v0.27.1/mlx_lm/generate.py) 与 [缓存代码](https://github.com/ml-explore/mlx-lm/blob/v0.27.1/mlx_lm/models/cache.py)。这里只讨论标准 target KV cache，不推断所有缓存类型或另一个 draft model 的状态处理。

### 7.5 实现未定时怎样写才准确

更一般的记法是：

```text
R(k) = sum(P(A = j) * E[T_recovery(k, j) | A = j], j = 0 ... k)
```

A 是接受前缀长度，T_recovery 由实际恢复路径决定。这个写法是解释不同成本模型的统一记号，不是已经实现的新控制器。

教授要求“按照 mlx-lm Cache Recovery 图更新 R(k)”的核心，是让流程、公式和实验中的实际动作一致：图画 trim，公式就不能仍然默认 replay。若实验实际执行 replay，则必须说明是另一条实现路径，而不能为了配合图而删除真实开销。

**目前本机短样例支持 trim-only 路径在这些样例上保持输出一致；它还不能证明所有任务都可以省掉 replay。** 如果后续发现差异，需要记录并排查。任何补救前向都必须进入计时，不能用基线答案静默修复轨迹。

## 8. 什么可能成为研究贡献

研究提案的重点是：在本地历史草稿解码中，以单位输出 token 的预计执行时间为依据，显式比较“不复用”和不同复用长度，并评估这个选择规则在相同历史来源下的额外作用。

支撑这项贡献需要形成一条完整证据链：

1. 说明原有实现的时间花在哪里，为什么便宜草稿值得尝试。
2. 给出明确、可复现的控制规则，而不只说“动态优化”。
3. 与同来源的固定历史策略比较，分离草稿本身的收益与控制器收益。
4. 计入验证、查找、控制和实际缓存处理成本。
5. 在合适基线上检查完整输出，再看延迟与 Agent 工作流收益。

以下内容不宜单独当作原创点：普通 Transformer 实现、标准 KV cache、n-gram lookup、使用旧代码、一般性的动态长度、把一个策略移植到 Mac。

## 9. 外部 Claude 报告的设置和结果

本节所有数字都是用户采用的**外部报告值**，来源为 `docs/DECODING_RESULTS_Claude.md` 及其开头的用户订正。不是本机重新生成的逐任务统计，也不能根据这些均值伪造原始样本或置信区间。

### 9.1 共同设置

- Apple Silicon、18 GiB 统一内存。
- Qwen2-1.5B-Instruct-MLX，4-bit、group size 64。
- 贪心解码，每次调用最多 384 token，最多两次修复。
- 公共任务来自 MBPP sanitized 与 HumanEval，不是 MBPP+ 或完整仓库级 benchmark。
- 可见测试用于反馈，最终评分测试不进入提示。
- 原始队列为 60 个 MBPP sanitized 加 30 个 HumanEval。
- 新主队列为每个数据集 15 个任务，共 30 个任务、64 个固定请求，其中 34 次修复。
- 主队列执行三次打乱重复。实际 Agent 时间使用其中每个数据集前 10 个任务，共 20 个。

报告中的修复轨迹大量重复旧代码，而且主队列没有把失败首轮修复为最终成功。这影响结果的应用意义，但并不把相同输出的计时比较变成无意义。正确结论是“这类轨迹可以加速”，不能扩张成“Agent 更会修代码”。

### 9.2 主队列的模型耗时

| 方法 | 相对普通解码的模型时间加速比 | 报告中的 95% task-bootstrap 区间 |
| --- | ---: | --- |
| 普通 KV-cache 解码 | 1.000x | 参考 |
| 固定历史草稿，k<=16 | 1.450x | 1.340-1.560 |
| 成本控制器，k=0/2/4/8/16 | 1.650x | 1.520-1.780 |
| 简单接受率规则，k<=8 | 1.250x | 1.180-1.340 |

报告称这些运行完整输出匹配。固定历史在 MBPP/HumanEval 分别约 1.43x/1.46x，动态控制约 1.64x/1.66x。它们是这组任务的结果，不是对任意 Agent 的预测。

动态相对固定的比值为：

```text
1.65 / 1.45 = 1.1379，约为 1.14x
```

这约为 14% 更高的处理速度，不是减少 14% 耗时。对应固定到动态的时间减少约为 `1 - 1.45/1.65 = 12.12%`。

### 9.3 Repair-only 已收到明确订正

| 口径 | 固定历史 | 动态控制 |
| --- | ---: | ---: |
| 总体模型时间加速比 | 1.45x | 1.65x |
| 仅修复调用加速比 | 2.05x | 约 2.86x |

动态修复阶段应使用用户订正的约 2.86x，不继续引用原始正文里的 2.20x。总体与修复阶段的算术一致性已经检查通过，不应反复把它当作仍未解决的整理错误。

它们仍是不同分母的口径，不能把 repair-only 的 2.86x 写成整个 Agent 的加速比，也不能把总体和修复加速比相乘。

报告还给出动态接受率 91.5%、固定 86.0%，但动态修复目标前向数 2,650 反而高于固定的 2,412，普通修复为 11,046。前向数并不等价于总时间；不同执行形状和恢复开销使“调用更少”不自动等于“更快”。这些数字需要外部原始记录才能进一步归因。

### 9.4 实际 Agent 时间

| 方法 | 每任务平均 Agent 时间之和 | 相对普通解码加速比 |
| --- | ---: | ---: |
| 普通解码 | 201.51 s | 1.000x |
| 固定历史 | 139.94 s | 1.440x |
| 成本控制 | 124.39 s | 1.620x |

这些时间是 20 个任务逐任务平均值之和，不是每个任务都耗时 201 秒。固定和动态的报告区间分别为 1.280-1.580、1.450-1.760。Agent 时间包括提示处理、可见测试、反馈与日志，不包括加载、预热和最终留出评分。

### 9.5 Native model/cache 扩展

外部报告还在 native mlx-lm 模型和缓存组件上，使用共享同步循环比较了不同策略：固定历史 1.34x、动态控制 1.60x、接受率规则 1.14x。

这支持“历史方案并非只在自定义模型/缓存上有收益”的报告结论。但它不是完整 `stream_generate` API，更不等于已经击败 mlx-lm 最快生产配置。

### 9.6 反馈版揭示的适应问题

第三组 20 个公共任务中，报告值为：固定历史 1.45x，原成本控制器 1.20x，带 fallback feedback 的控制器 1.60x。

因此不能说原成本控制器在每组任务都优于固定历史。反馈版试图处理的问题是：低接受估计使控制器长期退回普通解码，而退回后又缺少新的接受观察，导致难以恢复投机。

另一个 10 任务实际 Agent 小队列中，反馈控制相对普通 Agent 约 1.190x；没有定时固定历史对照，不能据此建立它相对固定历史的 Agent 优势。

### 9.7 受控编辑和固定长度消融的剩余核对

受控编辑使用 10 个作者任务，要求最终文件既保留旧行为，又满足新条件。报告称 7/10 通过，14 个固定请求重放比较，较大收益仍集中在两个失败任务的四次修复。

这里有一项已收到订正的比值：`1.295 / 1.136 = 1.1399648`，约 1.140x。**算术已解决，但 1.295x 最终属于哪一方法行、配套哪个区间尚未在本机材料中澄清。** 不要自行把某行 1.211x 或 1.218x 改成 1.295x，也不要给它拼一个旧区间。

固定长度后续消融报告给出 k=2/4/8/16 分别约 1.216x/1.292x/1.368x/1.450x。它先在验证集选择 k=16，再在复用的第三公共队列评估，不能算成额外独立任务队列。

消融表中的 dynamic 与讨论中的 feedback 身份、版本及配对区间仍需对应核对。可以介绍报告中的趋势，但不应把尚未对应清楚的方法标签和区间作为冻结的最终论文证据。

### 9.8 外部记录还缺什么

需要补齐最终方法版本、任务 ID、每请求每重复计时、输出一致性记录、校准配置、依赖版本、权重身份和执行后改动。外部原文的 checkpoint revision 为空；本机新 pilot 的 revision 不能不加说明地补进外部记录。

相同初始工程已获用户确认，不需要重建一个“完全未知”的项目。剩下的重点是把实际执行记录和方法标签对齐，而不是凭猜测宣布之前实验一定哪里写错了。

## 10. 11 月 17 日本机 mlx-lm API pilot

这一节是独立的新实测，原始记录在本机。它不使用外部报告均值作为输入，不复用已撤回研究作为有效证据，也不把外部修复轨迹当作算法可提前看到的历史。

### 10.1 到底接入到了什么程度

普通组直接调用安装的原生 `mlx_lm.stream_generate`。

固定历史组沿用同一个 streaming 函数的代码，通过一个隔离的函数命名空间替换底层 token generator。保留 native 模型、KV cache、EOS 处理、detokenization、response 构造和 wired-memory context。没有修改安装包文件或模块全局变量。

因此，准确说法是：**接入完整 streaming wrapper 的历史草稿扩展。** 不是 mlx-lm 已自带的历史草稿选项，也不是原来那条自定义同步循环；它仍是实验性适配器，不是所有生产功能都支持的通用 serving API。

扩展当前只支持贪心、标准未量化非旋转 KVCache；模型权重仍是 4-bit。权重量化与 KV cache 量化不是同一个配置。

### 10.4 计时边界

每个进程先预热两种模式，再做五组未计入主表的一致性验证，然后做 5 请求 x 2 方法 x 3 重复，共 30 次计时调用。

计时从准备消费 API 生成器开始，到完整消费、文本拼接和最终同步完成。包含 prefill、decode、草稿索引构建/查找、验证、裁剪、detokenization 和结果收集；不包含模型加载、预热、prompt/chat-template tokenization 和计时前 allocator cache 清理。

因此这是**预先分词请求的完整 streaming API 消费耗时**，不是原始文本进入到最终输出的所有准备开销，也不是完整 Agent 的工具执行时间。

诊断字段也有口径限制：新适配器的 `target_forwards` 包含显式 prefill 调用，而外部报告列出的修复 decode 前向数排除了初始 prefill，二者不能直接比较。`trim_s` 记录裁剪调用周围的 CPU 墙钟开销，不是独立校准的 GPU 验证时间；它本身不足以验证整个 R(k) 预测。无历史时走原生普通 API，扩展统计字段可能保持零，不能把它读成模型真的没有执行。

| 样例范围 | 不同请求数 | 普通耗时 | 固定历史耗时 | 普通/固定 |
| --- | ---: | ---: | ---: | ---: |
| 全部样例 | 5 | 6.906 s | 4.990 s | 1.384x |
| 已有历史的样例 | 4 | 5.860 s | 3.987 s | 1.470x |
| 其中三条行为修改 | 3 | 4.699 s | 3.335 s | 1.409x |

### 10.6 正确性与内存边界

case_insensitive 的输出把原拼写也改成了小写，没有完全满足任务要求，但两种解码输出相同。没有执行这些生成代码，也没有声称任务成功率提高。

确认进程的 MLX 峰值约 **1.003 GiB**，进程最大 RSS 约 **1.193 GiB**。这两种测量不是独立内存块，不能相加。runner 内记录的工作约 **18.28 秒**，不包括 Python 启动、导入和开发检查时间。

18 GiB 机器足够完成这次短样例测试，不需要先关闭其他应用。系统原先已有压缩和 swap，不能说这证明全程没有换页，也不能用这组峰值保证长上下文或并发运行的内存。

### 10.7 本机 pilot 证明和没有证明什么

它支持：历史草稿可以接入完整 streaming wrapper，且在这五条短样例上，trim-only 恢复保留了完整输出并获得初步计时收益。

它尚未证明：

- 动态控制器在完整 API 中优于固定历史。
- 长上下文、长输出或更大公共队列都无需 replay。
- KV cache 的全部元素与普通路径逐位相同。
- 已复现外部 1.45x/1.65x 或 Agent 1.62x。
- 真实仓库编辑、成功修复或生产部署都能获得同样收益。

**截至本文件日期，新的 API 适配器还没有动态控制策略。** 下一步不能只打开旧 `CostPolicy` 就当作已验证移植，因为旧恢复成本模型与新的 trim 路径不同。

## 11. 基线、指标与实验组织

### 11.1 必须分清的三类收益

| 比较 | 回答的问题 |
| --- | --- |
| 普通解码 vs 固定历史 | 历史草稿本身是否有效 |
| 固定历史 vs 动态历史 | 选择规则是否有额外收益 |
| 单请求模型时间 vs 完整 Agent 时间 | 推理收益能否传递到整个工作流 |

要评价控制器，固定与动态应共享目标模型、输入、历史来源、检索规则、验证器和恢复路径。不能一组用 replay、一组用 trim，然后把全部差异都归因于动态选择。

Native 方法应相对同一 native 普通路径检查输出。不要把不同推理实现之间的浮点差异自动算成某一优化方法的正确性问题，也不要忽略它们后继续声称跨引擎完整一致。

### 11.2 主要指标

| 指标 | 定义或需要记录的内容 |
| --- | --- |
| Model wall time | 明确边界的模型请求墙钟时间，包括算法附加工作 |
| Agent wall time | 模型、可见测试、反馈及框架开销；说明加载/预热/最终评分是否排除 |
| Speedup | 同一工作负载的基线时间除以方法时间 |
| Full output match | 全 token 序列、EOS/终止状态，必要时加文本和调用轨迹 |
| Task success | 按事先固定的最终测试或评分契约计算通过任务数 |
| Accepted/proposed | 接受的候选比例，不能单独代表加速 |
| Target forward count | 区分普通、批量验证、补救与 replay 的调用 |
| Lookup、decision、cache cost | 解释收益和瓶颈，不能从主计时中扣掉 |
| Memory | 区分模型权重、MLX allocation、进程 RSS 与系统压力 |

总体、首次生成、修复阶段、成功任务和失败任务应分开。不同数据集和任务队列不能只因汇总比值接近就合并。

三次重复用于降低计时噪声，不是三个新任务。正式不确定性分析应以任务为重采样单位，并保留方法之间的配对；不能把 token 或重复次数当作独立任务扩充样本量。外部报告已有的区间不能由本机五条样例替它重新确认。

### 11.3 防止数据泄漏

校准和评估任务应分开，在观察评估速度前固定任务列表与选择规则。只向 Agent 提供可见测试，最终留出评分结果不进入修复提示。

历史必须在该调用之前真实可见。固定输入重放可以使用基线轨迹中当时已有的旧代码，但不能把该调用未来生成的正确序列提前放进检索库。

代码测试需要隔离、超时和权限限制。现有 harness 是受限的本地研究工具，不是经过完备安全审计的通用恶意代码执行服务。

## 12. 目前可以怎样概括结论

可以这样介绍：

> 本研究在 Apple Silicon 上建立了可修改的 LLM 推理基础，分析了 KV cache 和小模型草稿的性能。随后研究利用代码 Agent 已有历史构造低成本草稿，并根据预计执行时间选择是否复用及草稿长度。外部研究报告给出了固定历史约 1.45x、动态控制约 1.65x 的模型时间结果。本机新的小规模测试进一步验证了历史草稿接入完整 mlx-lm streaming 流程的可行性，在五条短样例上保持输出并观察到收益。动态控制的 API 迁移、更大样本和有用编辑轨迹仍需完成。

## 14. 接下来应怎样推进

### 14.1 先扩大 native API 固定历史验证

冻结一组更接近实际修复的请求，增加输出长度和上下文长度；保留冷历史、长匹配、早拒绝、全接受、EOS 和长度上限等情况。

先检查完整输出，再比较计时。出现不匹配要保留，不选择性删除。需要判断差异来自验证逻辑、缓存位置、tokenization、停止规则，还是执行形状相关的浮点变化。

### 14.2 再接入与 trim 路径一致的动态策略

在固定策略通过更广范围检查之后，测普通 step、各 k 的验证成本、查找、裁剪和控制本身的开销。再让动态与固定使用相同 native 验证器和恢复方式。

移植时需要记录成本模型版本。旧 replay 公式可以保留为旧实现说明，新的 trim 成本规则需要自己的校准和验证，不能继承旧结果的标签。

### 14.3 证明控制器而不只是证明复用

用验证集选择合适的固定 k，再与动态策略在独立评估请求上配对比较。保留普通解码、简单接受率规则等对照，并检查是否只是“更长固定草稿”就能得到同样收益。

将预计较快的动作与实测耗时对照，分析误选和退回普通解码后的反馈问题。如果反馈机制产生收益，单独说明它相对原控制器的改变与成本。

### 14.4 扩展有用编辑和 Agent 时间

补充确实改变行为、最终通过旧行为与新要求检查的编辑轨迹。把复制失败答案、成功修改和失败修改分开，避免总体数字被重复失败调用主导。

随后跑完整 Agent episode，计入可见测试和反馈时间，检查输出、调用数及最终结果。单请求速度不能直接换算成 Agent 总体速度。

### 14.5 整理外部报告与冻结论文证据

取得外部原始结果后，优先对齐方法版本、表 6 订正对应行、表 7 dynamic/feedback 标签和配对统计。保存原文与订正，不静默替换旧 JSON。

论文正文可以先写背景、系统、算法和实验协议；结果章节应明确证据来源，在关键口径核对完成后冻结。当前不是“没有任何价值”，也不是“已经完成所有验证”。
